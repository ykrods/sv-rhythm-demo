# requirements: lib-placement

## 目的
`src/lib/` の使い方を見直し、関数・定数の置き場所を「どの画面から使われるか」で判断できるようにする。
あわせて、AI agent が実装時に迷わず判断できるように、関数に切り出す基準を明文化する。

## タスク種別
設計・ドキュメント更新・リファクタリング（ファイルの移動）

## 背景
- 現状の `src/lib/` は architecture 上「ゲーム内ロジック、複数のファイルから参照される定数」の置き場とされているが、1 つの画面でしか使わない関数も置かれている
- 音声 API に依存する処理（`src/lib/audio/`）は、「暗黙的な外部環境への依存を避けるゲームロジック」という `src/lib/` の方針と食い違ったまま暫定で置かれている（`tasks/20261113-audio-playback/requirements.md`「実装方針」）
- Health Check（2026-11-16）で、`src/lib/audio/` の置き場所について判断できない点として指摘された

## 要件

- 方針に合わせて既存のファイルを移動し、import を修正する

### 配置の方針
- その画面でのみ使う関数・定数・クラス・svelte コンポーネント（以下、「関数など」と表記）は `src/scenes/<scene>/` 以下に配置する
- 複数画面で利用される関数、またはアプリケーションの特定の機能に依らない共通の関数などを扱うものは `src/lib/` 以下に配置する
  - 例1: このプロジェクトでの画面サイズは特定の機能によらず共通なため、 `src/lib/scene.ts` に定義する
  - 例2: アーキテクチャや共通仕様で「このアプリでは日付を以下のフォーマットで表示する」など記載された場合に、 `src/lib/` 以下に日付フォーマットを行う関数を配置するなど

- 元の各節からは重複する記述を削除し、必要に応じてまとめた箇所を参照する
- まとめ先: `docs/architecture.md`「設計方針」に「ソースコードの配置と分割」節を新設し、「ゲームロジックの分離」節を置き換える
  - coding-guidelines 「共通化」「lint の行数制限を超えた場合の分割方針」には、新設した節への参照のみを残す
- `docs/coding-guidelines.md` に「Svelte コンポーネント」節を新設し、以下を移して記述する

    - 単純なテキストなど、`<defs>` を持たず再利用もしない要素はコンポーネントにせず Scene に直接書いてよい

  - コンポーネントの置き場所に関する記述は「ソースコードの配置と分割」にまとめる
  - 以上により、architecture 「Scene 内コンポーネントの分割」節は削除する

### 関数に切り出す基準
以下の基準をドキュメントに明文化する。
- ゲームロジック（座標計算・スコア計算・ノーツの位置計算など）は純粋な関数として切り出す
  - 複数の手順からなる計算や、条件分岐を含む計算は切り出す
  - 1 つの式で書ける計算（例: `x={i * LANE_WIDTH}`）はコンポーネントに書いてよい
- ブラウザ API の呼び出し（音声の読み込み・再生など）は、UI の表示・操作に関係しない場合、`.ts` の関数として切り出してよい
- コンポーネント内に残してよい関数
  - コンポーネントの責務である UI の表示や操作に関わる関数。
    - 具体的にはイベントハンドラやコンポーネントの状態を更新する関数
  - lint の行数制限を超えておらず、かつ判断に迷う場合はコンポーネントに残す

#### テストの対象（`docs/architecture.md`「テスト」に記載する）
- 外部依存の有無はディレクトリでは区別せず、以下の基準を文書化することで判断できるようにする
- テストの対象は `src/` 以下の純粋なロジック（結果が引数のみで決まるもの）とする
- ブラウザ API（Web Audio、`fetch`、`navigator`、DOM など）に直接依存する関数はテストの対象外とする
  - 外部依存のある関数は外部 API の呼び出しに専念させて薄く保ち、計算・判定などは純粋関数に切り出してテストの対象とする
  - 例: `startTrack` はテストの対象外とし、再生位置の計算は `toAudioTime` に切り出してテストする
- 純粋なロジックでも、自明な処理（定数の定義、単純な値の受け渡しなど）はテストしなくてよい
  - すべての関数をユニットテストする必要はない

### その他の要検討事項
- 画面固有の関数のうち、音声 API など外部環境に依存するものと純粋なロジックを、`src/scenes/<scene>/` 以下で区別する
  - => ディレクトリなどでは区別しない
- 画面固有の定数（例: `lane.ts`）の置き場所。`docs/coding-guidelines.md`「共通化」の「複数のファイルから参照される定数は `src/lib/` に置く」との関係
  - => ドキュメントを更新し、画面固有の定数は `src/scenes/<scene>/` 以下に配置する
- `src/scenes/<scene>/` 以下にコンポーネントと関数（`.ts`）が混在することになるため、その区別の要否（サブディレクトリを設けるか等）
  - => 混在させて良い
- テストの配置（現状 `tests/` は `src/` の構成に対応しており、例: `tests/lib/judge.test.ts`）。移動したファイルのテストをどこに置くか
  - => 現状と同じく `src/` の構成に対応させてファイルを配置する
- テストの対象（現状 architecture では「`src/lib/` の純粋なロジック」）を、`src/scenes/<scene>/` 以下の関数にも広げるか
  - => 広げる。「`src/` 以下の純粋なロジックがテスト対象になる。
